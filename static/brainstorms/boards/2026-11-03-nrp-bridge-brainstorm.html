NRP-bridge: a Web2 Nondominium for NRP users

SoushAI analysis. Drafted by Soushi's AI assistant, reviewed and shared by Soushi.

NRP-CAS (Network Resource Planning and Contribution Accounting System) is the Django app Sensorica built with Lynn Foster and Bob Haugen in 2013; Valueflows came out of it, and Nondominium is its Holochain successor. The idea on this board: a full, working Web2 prototype that keeps what NRP users already do every day, but rebuilt on Nondominium's model (NDOs, custodians, governance rules, participation receipts). It serves three ends at once: a bridge for people who know NRP and not Holochain, a dry run of the migration of historic NRP data, and a clean handover from the old system to the new one.

Settled on 2026-11-03. Soushi set two rules: stay as faithful as possible to Nondominium's data structure and to Valueflows 1.0, and build the bridge, not an intermediate backend. The remaining calls were taken on SoushAI's lean while he was away, at his instruction to carry the work through the V; each says so, and any of them can be reopened at requirements. The findings come from reading Sensorica/VerdunNRP, the ERP-bridge, Nondominium's own docs and the Valueflows 1.0 TTL.

Same daily work,
new ground underneath.An NRP user logs hours, opens a project, checks inventory, exactly as before. Each record shows, beside it, what it becomes in Nondominium. The Web2 app is the bridge they walk across; the migration is the same mapping run on the history.

2What NRP-CAS is, read from its source

VerdunNRP is one Django app doing almost everything: an 11,825-line valueaccounting/models.py, 328 named screens, a small REST API. Read at its only commit on GitHub (7d047ff).

fact, with its sourcealready worksmodel to copygotcharisk
One app, the whole REA modelvaluenetwork.valueaccounting owns every model and view; equipment, board (a farm inventory kanban) and api add screens and endpoints but no models of their own.The model to map is one file, which makes the concept map tractable.
Contribution is a flag on an eventWork, cash and material contributions are all EconomicEvent rows with is_contribution and is_to_distribute. The daily screens are log_past_work, work_now, labnotes, contributions, contribution_history.The work log is the heart of NRP use; the bridge must make it at least as easy.
Exits for historic data exist
  • REST: /api/people, contexts, economic-events, contributions, resource-types, resources, units
  • CSV: contribution_events_csv, exchange_events_csv, cash_events_csv
  • JSON-LD views for agents and relationships
  • Django dumpdata on PostgreSQL, 70 South migrations documenting the schema
A migration can read an API or a dump; no scraping needed.
A project is an agentThere is no Project model. A project is an EconomicAgent with is_context=True, and context_agent foreign keys run through processes, commitments, events, exchanges and value equations.Projects and organisations are the same thing in NRP; Nondominium splits them (Group vs NDO).
Value equations distribute incomeValueEquation → ValueEquationBucket (percentage, filters) → ValueEquationBucketRule (per event type, a claim formula). A Distribution snapshots the formulas it used and creates Claim rows per agent.This is the OVN benefit-redistribution logic, and Nondominium has no live equivalent yet.
Ownership is a percentageAgentResourceRole.owner_percentage records who owns how much of a resource. Nondominium's property regime is built to make that uncapturable.The one concept that should not cross the bridge as it is.
The repo holds no historyThe fixtures (verdun.json, starters.json) are seed types only: event types, use cases, units. No agents, events or resources.Real migration needs a database dump from whichever instance people actually used.
Never production-stableNondominium's development report says the NRP-CAS prototype had stability and security limits that kept it from production deployment. The stack (Django 1.4, Python 2, DRF 2.4) is long out of support.Who still uses an NRP today, and on which instance, is the first fact to pin down.

4ERP-bridge and NRP-bridge

The ERP-bridge is the precedent: a Python proof of concept that pushes an organisation's ERP inventory into Nondominium through hc-http-gw, one way, the organisation signing as one agent. The NRP-bridge looks the same from far and differs where it matters.

idearisk
Reuse the protocol-bridge specprotocol-bridge-specifications.md already defines a Bun bridge (REST over the Holochain WebSocket, cache, job queue, signals) with a per-platform integration layer. NRP can be one more platform beside ERPLibre.One bridge codebase, two adapters, instead of a second bridge.
The mapper is the shared pieceThe ERP-bridge's bridge/mapper.py turns products into ResourceSpecificationInput and stock into EconomicResourceInput. The NRP mapper is the same shape, much wider.Write the NRP mapping once, in TypeScript, and use it in the prototype, the migration and the live bridge.
Organisation-as-agent breaks contribution accountingIf the bridge signs everything as Sensorica, every contribution and PPR lands on one key, and the reputation that governance reads is lost for the people who did the work.The ERP identity model cannot be copied as it is.

5Three shapes the Web2 version could take

"Web2 version" could mean three builds. Soushi ruled out shape 2: no intermediate backend, the bridge is the work. Shape 3 is the target, and the design system prototype is shape 1 running the bridge's own code against an in-browser stand-in for the conductor.

already worksmodel to copyrisk
Shape 1 is what this repo does wellDirections A to F already run on a shared mock store with localStorage, surface keys, comments and the screen map. A seventh surface with its own store (as F has) costs no new infrastructure and deploys with the site.Fastest to something people can click, fully functional in the browser, no server.
Shape 3 is the true bridgeSame screens, the data in a real conductor through the protocol bridge. Users never install Holochain; their records are Holochain records from day one.The end state, and it depends on the Bun bridge existing.
Shape 2 is a second backend to keep aliveA real database in Nondominium's model is useful for people who will not run a conductor, but it duplicates the zome logic (validation, custody, PPRs) in a server.Worth it only if the Web2 app is meant to live for years.

6Migration and handover

The same mapping, run on the history. The picture below assumes a one-way import that can be replayed, with each person claiming their own key at handover; the cards decide whether that holds.

ideagotcharisk
Keep provenance on every migrated recordEach record carries the NRP table and id it came from, so a member can see "this contribution is NRP event 4123" and a replay never duplicates.Makes the import idempotent and the handover auditable.
History needs a validatorIn Nondominium a Contribution is validated by at least one Accountable Agent. Ten years of NRP work events have no such validation.Either mark migrated work as legacy-validated, or ask current Accountable Agents to re-validate in bulk.
Historic data stays out of this repoThis design system is public. Member names, hours and money from a real NRP must never be committed here.The public prototype runs on synthetic data shaped like NRP; a real dump is imported only on a local machine.

7Two fidelity targets: Nondominium and Valueflows 1.0

Soushi's rule: the bridge is as faithful as possible to Nondominium's data structure and Valueflows 1.0 compliant. Read against crates/shared/src/types.rs, zome_resource/src/lib.rs and the Valueflows 1.0 TTL, the two agree on most of the model and disagree in four places.

Membership has no Valueflows classValueflows 1.0 dropped agent relationships from the core TTL. NRP's AgentAssociation and Nondominium's GroupMembership both sit outside it.Membership stays a Nondominium entry; the export says so instead of inventing a Valueflows term.
One quantity, one custodianNondominium's EconomicResource has quantity and custodian; Valueflows 1.0 splits accountingQuantity from onhandQuantity and names primaryAccountable. Under the nondominium regime nobody holds the rights, so custody is the on-hand side.Export custodian as the holder of vf:onhandQuantity, and leave vf:primaryAccountable empty for nondominium resources.
Actions differ at the edgesNondominium's VfAction has InitialTransfer and AccessForUse, which Valueflows 1.0 lacks, and lacks transferAllRights, pickup, dropoff, deliverService and copy, which it has.The bridge writes Nondominium's actions and exports the two extras under a Nondominium namespace.
Units are stringsNondominium stores unit: String; Valueflows wants a vf:Unit with an OM-2 identifier. NRP's Unit rows carry names and abbreviations.The bridge keeps a small unit table mapping NRP units to OM-2 ids and writes the symbol Nondominium expects.

8Settled calls

Each call below is now a fact for the requirements stage. "Soushi" marks his own words; "lean" marks a call taken on SoushAI's lean while he was away, open to reversal.

1. The bridge, no intermediate backend (Soushi)Shape 2 is out. The target is shape 3, NRP-like screens over a real conductor through the bridge. Until the conductor is wired, the design system runs the same bridge code against an in-browser port that mirrors the zome calls of docs/prototypes/BACKEND.md.
2. Fidelity first (Soushi)Records are Nondominium entries, shaped as the zomes define them, and every one exports as Valueflows 1.0 JSON-LD. Where the two disagree, Nondominium's entry is what the bridge writes and the difference is named as a Nondominium extension in the export.
3. Its own section, /nrp (lean)A section of the design system with its own store, beside the hub's other surfaces, using the tokens, ndo-ui, comments and the screen map.
4. First round covers work, contributions, projects, resources (lean)Work log, my contributions, projects and members, resource types and inventory with custody, and the migration view. Value equations are shown as what they become (an Agreement) and get their own brainstorm.
5. A project becomes a Group (lean)Its outputs become NDOs inside it.
6. Each member claims a key (lean)History is written under a person's key only after they claim it; unclaimed history stays visible in the bridge as pending.
7. Repeatable one-way import until cutover (lean)Idempotent by NRP provenance; NRP goes read-only at cutover.
8. Synthetic data in public (lean)A synthetic NRP dataset shaped like VerdunNRP's tables; real dumps only on a local machine.
9. NRP is an adapter of the protocol bridge (lean)The NRP mapper and identity policy are one adapter; transport and zome calls are the protocol bridge's.
