Architecture

Commitment Pool MVP (Tibi's experiment)

The architecture of Tibi's commitment-pool-experiment branch at 057c5eb, drawn as it stands: a Group is a pool, a Commitment lives on its NDO, and fulfillment is one closure that writes the event, the claim and two verifiable receipts. Every box marked new or modified is what the branch adds over dev at 91cfd11; unmarked boxes are already on dev. Each box's spec says in words what of it is on dev and what is branch only; the code snippets are read at the branch head, so a snippet of a file dev also has can differ from dev by the lines the branch adds. The general backend came to dev through #183; the pool itself is on the branch, which has no PR because it is not meant to be merged.

Updated on 17 November 2026. Checked against dev at 91cfd11 and the branch at 057c5eb, and against the 17 November Lab meeting with Tibi. dev has not moved in code since #183 (its one later commit, #215, changes a README badge), so what #183 brought is now marked as on dev box by box: commitments per NDO, the fulfillment closure, Measure and the Layer 1 foreshadow fields. The branch gained two commits: new commitment and event forms (2f5834c), and a refusal of a commitment whose provider and receiver are the same agent, with its Sweettest and a participation grammar spec (057c5eb); both are branch only. The meeting decided that project management lives in the work context, not in the NDO: that settles nothing on the pool, but it adds D6 (where a pool attaches once work contexts exist) and a line to D5. The local PR-board link is gone so the page can be published; the branch review's line-level findings stay off this page.

How to work it: walk the maps (double-click a box to open its level), open a box for its spec, then pick on each decision card. The decisions are only the ones that concern dev; the experiment's own calls are Tibi's, listed under Evidence, and the open points on the pool's authorisation stay findings of the branch review.

My lean, Capability slots in v0.2, work contexts in v0.3: Two open issues already wait on the slot substrate; work contexts have no waiting consumer yet.

Consequences: Soushi, 2026-11-13 16:13 and 16:32: slots (#184) in v0.2, work contexts (#201) in v0.3. v0.2 lanes: Soushi on hREA and slots, Tibi on NDO Layer 1 (#206, #207, #141, #144), plus the standalone release (#203). D6 Once work contexts are on dev, where does a pool attach? proposed

Opened 17 November from the Lab meeting: project management lives in the work context, not in the NDO, because one NDO can have several teams, each with its own project management (journal, Décisions, first point, P1 3 to 10). ADR-014 puts work contexts in the group DHT and has them name NDOs by clone coordinates, as NdoAnchor does (documentation/specifications/adr/ADR-014-work-contexts-in-group-dht.md, lines 25 to 31). The branch makes the Group itself the pool: CommitmentAnchor carries a group_hash and nothing about a work context (zome_group_integrity lib.rs at 057c5eb, lines 112 to 130). Work contexts are v0.3 (#201) and have no code yet; the meeting did not talk about the pool.

My lean, Settle it in the design of #201, with the pool named as a consumer: Neither the meeting nor ADR-014 says anything about pools, and the work-context entry does not exist yet, so the cheapest moment is the design of #201.
